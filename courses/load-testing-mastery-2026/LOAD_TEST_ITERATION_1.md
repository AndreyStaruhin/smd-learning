## 1. Цель итерации

Найти **стационарный предел пропускной способности нижней части системы digitalprofile.individuals** при двух конфигурациях воркеров `queue-person-executor`: **N=5** и **N=10**. Результат — материал для разговора с командой о выборе финальной конфигурации воркеров к ближайшему релизу.

Тип итерации — **рабочий**, не разведочный. Результат должен быть в форме, переносимой в команду (см. §9).

## 2. Объект измерения и точка инжекции

### 2.1 Объект измерения

Измеряются как одна подсистема:

- HTTP-обработчик входящих сообщений реверс-СМЭВ-API;
- создание задачи в `tasks` через `StartScenarioEvent` → `TaskReadyToCreateEvent`;
- воркеры (`PersonQueueTaskHandler`, `queue.executor.threadPoolSize=N`);
- PostgreSQL (выборка через `SELECT FOR UPDATE SKIP LOCKED`, INSERT в `tasks`/`history`).

### 2.2 Точка инжекции — реверс-СМЭВ-эндпоинт

«Реверс-СМЭВ» — историческое название направления **«гейт → наш сервис»** через TLS HTTP. Появилось, когда направление обращения «развернулось»: раньше наш сервис сам отправлял запросы в гейт, теперь гейт отправляет нам. Технически это входящий HTTP-API сервиса под `/smev/api/v1/*`.

**Кандидат-эндпоинт по умолчанию:** `POST /smev/api/v1/PersonalData` (см. также открытый вопрос §13.10 про альтернативу `/CustomerPermissionList`).

| Поле | Значение из кода |
|---|---|
| URL | `/smev/api/v1/PersonalData` |
| Класс/метод обработчика | `PersonsSmevController.receivingPersonalDataDocuments()` (`PersonsSmevController.java:56-87`) |
| Формат тела | **JSON** (контроллер настроен с `consumes = APPLICATION_JSON_VALUE`) |
| DTO тела | `ReceivingPersonalDataDocWithScopeSmev3Request` (с `@Valid`) |
| Обязательные заголовки | `X-Bank-Id` (UUID), `X-Request-Id` (String) |
| Опциональные заголовки | `X-Repository-Id` (String), `X-Protocol-Type` (enum `ProtocolType`) |
| Тип задачи в очереди | `PersonalDataDocumentsRequest` (через `DataType.RECEIVING_PERSONAL_DATA_DOC_REQUEST` → `QueueTaskTypeMapper.map(...)`) — см. §2.6 |

### 2.3 Что обработчик делает синхронно ДО возврата 200 OK

Из кода `SmevService.handle()` (вызывается из `PersonsSmevController:81`):

1. `sendAdapterRequest(...)` — **исходящий SOAP-вызов в СМЭВ-адаптер** через `adapterRequestExecutor.sendRequest(...)` (на стенде — WireMock-стаб, задержка ~150 мс).
2. `prepareScenarioData(...)` — маппинг в `GetResponseStageData`.
3. `createSmevScenario(...)` → `publisher.publishEvent(StartScenarioEvent)` → синхронный `@EventListener` `ScenarioEventService.handleStartScenarioEvent` → `publisher.publishEvent(TaskReadyToCreateEvent)` → запись задачи в `tasks` (через handler-listener).
4. **Только после этого** контроллер возвращает `200 OK`.

> **Наблюдение Claude Code (фактчекинг):** на каждый POST реверс-СМЭВ-эндпоинт сервис **синхронно** делает один SOAP-вызов в СМЭВ-адаптер (на стенде — WireMock ~150 мс). Затем создаётся задача со стадией `GetResponse`, которую воркер обработает асинхронно — и в стадии `GetResponse` будет ещё один SOAP-вызов в адаптер. То есть один POST → **два WireMock-вызова**: первый синхронно во входе, второй в воркере (на разных шагах жизненного цикла). Этот факт является **открытым вопросом для интерпретации** результатов (см. §13.7).

### 2.4 Что нужно мокировать

Помимо уже принятых WireMock-стабов из `LOAD_TEST_PLAN.md` §3 (СМЭВ-адаптер на `SmevOptions.AdapterUri`, Gate-out на `Gates.AbsGateUri`) — **дополнительных стабов не нужно**. Внешний ТР ЕСИА в этом сценарии не задействован: цепочка `/cb` не используется, аутентификация пользователя не происходит.

### 2.5 Минимально необходимые поля тела

**Формат тела — JSON.** Тело POST на реверс-СМЭВ-эндпоинт `/PersonalData` — это JSON, не SOAP-конверт. SOAP-обёртка живёт **внутри обработки** (исходящий запрос от продукта в адаптер, см. §2.3), не на входе. Это уточнение существенно: в более ранней работе по плану формат тела на входе обсуждался в одном ряду с SOAP-форматом адаптера, и это вело к путанице.

Тело должно проходить `@Valid`-проверки `ReceivingPersonalDataDocWithScopeSmev3Request`. Конкретный набор обязательных полей зафиксирован Bean Validation-аннотациями этого DTO. Шаблон фиксированный — мы не тестируем валидацию.

**Открытый вопрос (см. §13.8):** какой минимально-валидный JSON, проходящий все `@Valid`-проверки? Это вопрос **составителя Gatling-сценария на следующем шаге**, не часть этого плана.

### 2.6 Связь endpoint → task_type (наблюдение M1.14)

POST `/smev/api/v1/PersonalData` с JSON-телом, содержащим массив `dataTypes` (например, `["inn", "RF_PASSPORT"]`), создаёт в очереди **одну** задачу типа **`PersonalDataDocumentsRequest`**. Связь endpoint → task_type идёт через xsd-описание вида сведений (`PersonalDataDocumentsRequest` — это имя ВС в реверс-СМЭВ).

**Не создаются** при этом запросе: `PersonalDataRequest`, `CustomerPermissionListRequest` — это другие виды сведений со своими endpoint'ами.

**Следствие для метрик дашборда (см. §6, §7):** отслеживать в первой итерации нужно конкретно `taskType="PersonalDataDocumentsRequest"`, а не агрегированный фильтр и не другой task_type.

**Эмпирическая проверка (M1.14):** smoke-прогон 50 POST на `/PersonalData` (`constantUsersPerSec(5).during(10)`) → +50 в Counter `dp_queue_tasks_processed_total{result="success", taskType="PersonalDataDocumentsRequest"}`. Все 50 задач дошли до финального успешного статуса (COMPLETE).

> **Наблюдение для Claim Scope:** в более ранних редакциях плана и в чек-листе сценария A фигурировал `taskType="PersonalDataRequest"` — это **расходилось** с фактической связью endpoint → task_type. Имя поправлено в M1.14 после первого прогона.

## 3. Claim Scope результата

Результат относится к **нижней части системы**. Узкое место в верхней части (`/cb`-цепочка, реальная аутентификация ТР ЕСИА, валидация `customerUuid` в `CbEsiaService.validateCustomerUuid`) этим тестом **не находится**.

**Не входит в критерий приёмки этой итерации:**

- **Латентность отдельной задачи в очереди** (`task_latency_in_queue`). Если бизнесу окажется важна — отдельная итерация.
- **Burst-сценарии** (способность переваривать пики). Меряем только **стационарную пропускную способность**.
- **Сравнение с REST-сценарием A или комбинированной нагрузкой C** (см. base plan §5, §6.1).
- **USE-метрики ресурсов** (CPU, GC, Hikari) — не входят в первичное решение по итерации (см. §7.1, §13.4).

### 3.1 Идеализации стенда (что НЕ моделируется WireMock-стабом)

Дополнительно к перечню «не входит в критерий приёмки», что мы измеряем — это поведение системы на **идеализированном** стенде. WireMock-стаб СМЭВ-адаптера моделирует адаптер в свёрнутом виде по пяти осям. Этот раздел — частный случай `LOAD_TEST_PLAN.md` §4.1 для первой итерации; источник записан там.

1. **Матчер WireMock работает по содержимому XML, не по SOAP-структуре.** Проверено эмпирически: голый XML с правильным элементом `<ACTION>` сматчится так же, как полный SOAP-конверт. Изменения SOAP-обёртки в проде (другой namespace, дополнительные header'ы, другой порядок элементов, дополнительный `<soap:Header>`) стенд **не отлавливает**. Стаб ответит так же, как на полный конверт.

2. **Адаптер всегда отвечает 200 OK с `SUCCEEDED`.** Не моделируются:
   - HTTP-ошибки 5xx и таймауты на запросах в адаптер;
   - SOAP-ответы со `statusResponse` отличным от `SUCCEEDED`: `PROCESSING` (ещё не готов), `FAILED` (СМЭВ вернул ошибку), `NO_DATA` и т.п.

   Каждое из этих условий запускает в продукте **свой код** — обработка ошибки, ретраи, дочернее изменение состояния задачи. Этот код на нагрузочном тесте **не выполняется ни разу**. Тест меряет только «счастливый путь».

3. **Адаптер не имеет собственной пропускной способности.** В проде адаптер — это компонент со своими ресурсами (его собственная очередь, контейнер, throttling, contention на внутренней таблице «MessageID → готовый ответ»). На стенде он отвечает с фиксированной задержкой 150 мс независимо от concurrency: при росте RPS на стенд latency адаптера не растёт, в проде — растёт.

4. **Polling-семантика стадии GetResponse свёрнута к одному обращению.** В проде воркер с задачей `MessageID=AAA` обращается к адаптеру за конкретным сообщением. Если адаптер ещё не готов — продукт получает не-`SUCCEEDED` статус, задача возвращается в очередь, через интервал берётся снова. Один бизнес-запрос порождает **N** обращений к адаптеру в стадии GetResponse за время жизни задачи (median зависит от реального времени готовности ответа в СМЭВ-3 — секунды или больше). На стенде N **свёрнуто к 1**: каждая задача закрывается с первого `GetResponse`. Это даёт **систематически завышенный потолок стенда относительно прода**:
   - на стенде задача физически **меньше** держит воркера, чем в проде;
   - суммарная нагрузка на адаптер на стенде в N раз **меньше** прод-нагрузки при том же бизнес-RPS;
   - `dp_queue_tasks_backlog_size` в проде имеет другой характер — задачи дольше «висят», backlog пульсирует.

   Это **главный** источник смещения «предельный RPS на стенде» vs «предельный RPS в проде».

5. **`MessageID` в `GetResponseRequest` игнорируется WireMock'ом.** В проде адаптер маршрутизирует ответ по `MessageID` запроса (своя таблица «MessageID → готовый ответ»). На стенде маппер сматчится только по `ACTION`, ответ всегда один и тот же с захардкоженным `OriginalMessageId=11111111-...`. Эффекты прод-уровня (поиск по индексу адаптера, contention на этой таблице, обработка дубликатов или поздних ответов) на стенде отсутствуют.

**Следствие для интерпретации итогового числа.** «Предельный RPS на стенде» **не равен** «предельному RPS в проде». Главный источник смещения — пункт 4 (polling), он смещает потолок **в сторону завышения**: стенд показывает оптимистичную верхнюю оценку. Перенос результата на прод требует калибровки на median N в прод-логах за репрезентативный период (см. §13.13). Калибровка **не входит в эту итерацию** — это задача команды по итогам прогона.

### 3.2 Идеализации сценария A первой итерации (что НЕ моделируется на стороне инжекции)

К идеализациям стенда (§3.1) добавляются идеализации **самого тестового сценария** — это то, что мы упрощённо моделируем на стороне Gatling-инжекции. Они не «недостатки» — это **сознательные упрощения** первой итерации, которые позволяют интерпретировать результат и в следующих итерациях расширять модель целенаправленно.

1. **Один SNILS на все запросы.** В сценарии используется захардкоженный SNILS (`263-237-610 61`), не feeder с уникальными значениями. Эффекты прода (распределение SNILS по диапазонам, индексные операции БД на уникальных значениях, дедупликация по SNILS если она есть в продукте) на стенде не воспроизводятся. Решение осознанное: дедупликация по SNILS на уровне продукта в M1.12 проверена и **не препятствует** обработке в текущей реализации; для первой итерации валидно.

2. **Один X-Bank-Id на всю симуляцию.** Заголовок `X-Bank-Id` фиксирован (`00000000-0000-0000-0000-000000000001`). Сценарии с несколькими банковскими стендами / multi-tenant-нагрузкой первой итерацией не покрываются.

3. **Один task_type — `PersonalDataDocumentsRequest`.** Симуляция дёргает только endpoint `/PersonalData` → создаются только задачи `PersonalDataDocumentsRequest`. Смешанная нагрузка (одновременно `PersonalDataDocumentsRequest` + `CustomerPermissionListRequest` + другие) первой итерацией не покрывается. Это значит: эффекты contention между разными `task_type` на одной таблице очереди — на стенде не воспроизводятся.

4. **Фиксированный набор `dataTypes` в теле.** Тело POST содержит массив `dataTypes: ["inn", "RF_PASSPORT"]` без вариативности. Прод-нагрузка содержит другие комбинации; их влияние на размер обработки в воркере — открытый вопрос (см. §13.21).

**Следствие для интерпретации.** Первая итерация даёт результат для **одного типа задачи в одном банке от одного клиента**. Перенос на «общую пропускную способность системы» требует отдельной работы по моделированию реального распределения task_type / банков / dataTypes — это задача следующих итераций.

## 4. Профиль инжекции

Ступенчатый ramp-up. Шаг ступени привязан к теоретическому потолку throughput.

**Расчёт теоретического потолка:**

- WireMock-задержка на внешний вызов = 150 мс.
- Оценочное время обработки одной задачи воркером ≈ 200 мс _(подлежит проверке — см. §4.1)_.
- Теоретический потолок при 5 воркерах ≈ **25 RPS**.
- Теоретический потолок при 10 воркерах ≈ **50 RPS**.

| Конфигурация | Шаг ступени | Ступени RPS | Длительность плато |
|---|---:|---|---:|
| **N=5** воркеров | 5 RPS | 5 → 10 → 15 → 20 → 25 → 30 | 2 мин (ориентир) |
| **N=10** воркеров | 10 RPS | 10 → 20 → 30 → 40 → 50 → 60 | 2 мин (ориентир) |

**Переходы между ступенями** — несколько секунд (не мгновенно), чтобы избежать сетевых артефактов на API.

**Длительность плато 2 минуты — первая попытка**, корректируется на первом прогоне по форме реальных графиков.

### 4.1 Открытый вопрос: точное `T_task`

Допущение `T_task ≈ 200 мс` требует сверки по коду.

**Из кода видно**, что обработка одной задачи стадии `GetResponse` воркером включает:

- `taskRepository.getNextPerson(...)` — SQL `SELECT FOR UPDATE SKIP LOCKED` + перевод задачи в `running=true` (`PersonQueueTaskHandler:51`).
- Десериализация `data.jsonData()` в `GetResponseStageData` (Jackson, `ScenarioEventService.handleTaskReceivedEvent`).
- `scenario.executeStage(...)` для стадии `GetResponse` — внутри **исходящий SOAP-вызов в адаптер** (WireMock ~150 мс), плюс анализ ответа.
- Публикация результата (`TaskCompletedEvent` / `TaskExecutedWithTransientErrorEvent` / ...).
- SQL смены статуса в `tasks` + INSERT в `history`.

**Дополнительно** см. §2.3: сам POST на реверс-СМЭВ-эндпоинт уже сделал один WireMock-вызов синхронно во входе **до** создания задачи. То есть лимитирующая операция «WireMock 150 мс» встречается дважды на «POST → задача обработана», но в **разных** местах жизненного цикла (HTTP-вход и воркер).

Является ли `T_task ≈ 200 мс` корректной оценкой для нашего реального жизненного цикла или фактическое значение существенно другое — **открытый вопрос (см. §13.1)**, проверяется на warm-up первого прогона.

> **Связь с §3.1 п. 4.** На стенде стадия `GetResponse` всегда завершается с первого вызова (всегда `SUCCEEDED`). В проде — N вызовов на бизнес-задачу. `T_task` на стенде по этой оси — **нижняя оценка** прод-`T_task` для одного бизнес-запроса. Это означает: даже точное `T_task` стенда даст потолок выше прод-потолка. См. §13.13.

## 5. Первичный маркер останова ступени

**Метрика:** `dp_queue_tasks_backlog_size{taskType="person"}` (Gauge — спецификация в `LOAD_TEST_PLAN.md` §7).

> **Тег `taskType="person"` для Gauge сохранён** (агрегация по 3 PERSON-типам через фильтр в SQL, реализация в `QueueMetrics.@PostConstruct`, M1.11). Это содержательная асимметрия с Counter, который использует разбивку по конкретному `taskType` (см. §6.2 и §13.20).

### 5.1 Критерий стационара (визуальный, первая попытка вербализации)

На каждой ступени оцениваются **две фазы**:

1. **Переходная** — после повышения темпа RPS, backlog растёт (или резко скачет).
2. **Стационарная** — после выхода на новый уровень.

**Стационар признаётся:** на стационарной фазе средняя линия backlog **не возрастает** относительно первой минуты этой фазы (визуально, без формального порога).

**Стационар не признаётся:** на стационарной фазе средняя линия продолжает расти, новое плато не достигается до конца ступени.

> **Уточнение по итогам M1.14 (см. §7.3):** на низких ступенях (5 RPS, 10 RPS) Gauge backlog ожидаемо может быть нулевым / прерывистым из-за интервала scrape (15 сек) vs времени жизни задачи (доли секунды). Это **не** означает, что нагрузка не идёт — это означает, что затора нет. Для проверки факта работы нагрузки на низких ступенях смотреть Counter rate (см. §7.3).

### 5.2 Вердикт по конфигурации

> Предельный RPS = последняя ступень, на которой стационар признан.

**Точность результата** = шаг ступени (5 RPS для N=5, 10 RPS для N=10).

### 5.3 Открытый вопрос: формальный критерий стационара

Окно наблюдения и порог скорости роста для формального критерия **не сформулированы**. Разрабатываются на основе наблюдений первого прогона и **переходят в следующую итерацию**.

В рамках этой итерации критерий — **визуальный**, его выносит исполнитель прогона на дашборд Grafana.

## 6. Вторичные маркеры

Используются для **интерпретации результата**, не для принятия решения «прошла ли ступень».

### 6.1 Ошибки на входе HTTP реверс-СМЭВ

```promql
http_server_requests_seconds_count{uri=~"/smev/api/v1/.*",status=~"4..|5.."}
```

с группировкой/фильтром по `status` и `uri`. Это стандартная Spring Actuator метрика — отдельных кастомных метрик не требует.

### 6.2 Ошибки в обработке (внутри воркеров)

```promql
dp_queue_tasks_processed_total{result="fail",taskType="PersonalDataDocumentsRequest"}
```

(спецификация метрики в `LOAD_TEST_PLAN.md` §7).

**Семантика Counter (зафиксирована при реализации в M1.12, β):** Counter инкрементируется только на **финальных** исходах задачи — `COMPLETE` → `success`, `FAIL` → `fail`. Промежуточные статусы (`TRANSIENT_ERROR`, `NOT_READY`, `CHANGE_STATE`, `COMPLETE_AND_CREATE_NEXT`) **не считаются** как отдельные результаты — задача в этих статусах ещё не закончила жизнь и доберёт `success` или `fail` позже.

Соответственно `result="transient_error"` в Counter **не существует** — следить нечего.

**Если в первой итерации возникнет потребность мерить «временные ошибки во время обработки»** — это отдельный сигнал, не покрываемый текущим Counter. Подход к нему — открытый вопрос (см. §13.18).

**Тег `taskType="PersonalDataDocumentsRequest"`** соответствует фактической связи endpoint → task_type для сценария первой итерации (см. §2.6). В более ранних редакциях здесь использовалось `taskType="person"` — это было неточно, исправлено в M1.14.

### 6.3 Правила интерпретации

Графики выводятся **раздельно**. **Не суммируются** — это разные физические механизмы (насыщение верхней vs нижней части трубы).

### 6.4 Открытый вопрос: пороги допустимой ошибки

Пороги «допустимой» ошибки на каждом графике в первой итерации **не выбраны**. Записывается **фактический** error rate, без приёмочных порогов.

## 7. Метрики дашборда первой итерации

Минимально достаточный набор, отвечающий на два связанных, но **разных** вопроса:
1. «Накапливается ли затор в очереди?» (первичный маркер останова ступени по §5)
2. «Какой поток задач реально обрабатывается?» (для проверки факта нагрузки и интерпретации результата)

Различение этих двух вопросов и выбор инструментов под каждый — см. §7.3.

| Назначение | Вопрос, на который отвечает панель | Метрика / выражение | Тип | Источник |
|---|---|---|---|---|
| Первичный — затор | Накапливается ли затор в очереди? | `dp_queue_tasks_backlog_size{taskType="person"}` | Gauge | base plan §7 (кастомная) |
| Первичный — поток | Какой поток успешно обработанных задач? | `rate(dp_queue_tasks_processed_total{result="success",taskType="PersonalDataDocumentsRequest"}[1m])` | Counter | base plan §7 (кастомная) |
| Вторичный — ошибки на входе | Появляются ли ошибки HTTP-уровня? | `rate(http_server_requests_seconds_count{uri=~"/smev/api/v1/.*"}[1m])` by `status` | стандартная Spring | Spring Actuator |
| Вторичный — ошибки обработки | Появляются ли финальные сбои задач? | `rate(dp_queue_tasks_processed_total{result="fail",taskType="PersonalDataDocumentsRequest"}[1m])` | Counter | base plan §7 (кастомная) |
| Контекстная — текущая ступень | Какой сейчас инжектируемый RPS? | `rate(http_server_requests_seconds_count{uri=~"/smev/api/v1/.*"}[30s])` | стандартная Spring | Spring Actuator |

**Дисциплина именования панелей:** на дашборде каждая панель подписывается **по вопросу**, на который отвечает (колонка 2), а не по имени метрики. Это удерживает читателя дашборда в осознании, что именно показывает картинка.

**Ограничение:** в первой итерации **не делаем** панелей «индикатор стационара» (зелёный/красный). Критерий — визуальный, формализованных индикаторов нет.

### 7.1 Открытый вопрос: USE-метрики

USE-метрики (CPU `process_cpu_usage`, RAM `jvm_memory_used_bytes`, Hikari `hikaricp_connections_pending`, GC `jvm_gc_pause_seconds`) — нужны как **контекст** или **нет** в первой итерации? Решение **отложено** до сборки стенда (M1.5).

### 7.2 Метрики из base plan §7, которые НЕ входят в дашборд первой итерации

Эти метрики **существуют** в спецификации base plan §7, но в первой итерации **не входят в дашборд решения**:

- `dp_queue_tasks_incoming_total` — потенциально полезен для расчёта `backlog_growth = incoming − processed`, но первичный маркер этой итерации — **абсолютный backlog**, не разница потоков. Использование — открытый вопрос для следующих итераций.
- `dp_queue_task_processing_seconds` (Timer) — относится к латентности, явно вне scope (см. §3).
- `dp_queue_workers_busy`, `dp_queue_tasks_stuck_total` — USE-метрики (см. §7.1).

### 7.3 Различение «затор» vs «поток» — два разных вопроса наблюдения (M1.14)

Эмпирически обнаружено в smoke-прогоне M1.14 (1–5 RPS × 10 сек): **Gauge `dp_queue_tasks_backlog_size` при малой устойчивой нагрузке показывает 0 или 1**, даже когда задачи реально обрабатываются и Counter `processed_total` растёт линейно (в smoke — на 50 за 10 сек при 5 RPS).

Причина — структурная: интервал scrape Prometheus = 15 сек, а время жизни задачи в очереди при потоке 5 RPS — доли секунды. Между двумя соседними scrape'ами в очереди успевает побывать ~75 задач, но в **момент** scrape из них видна максимум одна (та, что обрабатывается в этот миг).

**Это не баг Gauge и не «дашборд тормозит» — это фундаментальная природа pull-метрики при потоке быстрых событий.**

**Следствие — два разных вопроса требуют двух разных инструментов:**

| Вопрос | Инструмент | Когда срабатывает |
|---|---|---|
| **Накапливается ли затор?** | Gauge `dp_queue_tasks_backlog_size` | Когда воркеры **не успевают** разгребать поток. Backlog становится виден ненулевым на нескольких scrape'ах подряд. |
| **Какой поток через очередь?** | `rate(dp_queue_tasks_processed_total[1m])` | Всегда. Для измерения потока Gauge backlog **в принципе непригоден** при низком backlog. |

**Как это задаёт первичные маркеры:**

- **Стационар по §5** (backlog не возрастает) — это вопрос «затор». Gauge — корректный инструмент.
- **Throughput** (сколько задач в секунду реально обрабатывается) — это вопрос «поток». Counter rate — корректный инструмент.

В первой итерации **первичный маркер останова ступени** — стационар backlog (как в §5). Но дашборд имеет **обе** панели — затор и поток (см. таблицу §7), и они подписаны по вопросу.

**Следствие для warm-up первого ramp-up-прогона.** На малых ступенях (5 RPS, 10 RPS) Gauge backlog ожидаемо будет нулевым / прерывистым — это **не** значит, что нагрузка не идёт. Чтобы это проверить — смотреть Counter rate. Расхождение между «Gauge показывает 0» и «Counter rate растёт» на низких ступенях — норма, не аномалия.

## 8. Tear-down между прогонами (открытый вопрос)

В рамках этой итерации проводится **минимум два прогона** — N=5 и N=10. Состояние между ними нужно приводить к одной точке. Решение **не принято в M1.4**, ниже — **развёрнутый список альтернатив без выбора**:

| Вариант | Что делает | За | Против |
|---|---|---|---|
| **A.** TRUNCATE `tasks`, `history`, `esia_operations` | Очистка таблиц очереди и операций | Чистая БД, повторяемость | Не убирает heap, JIT-кеши; `pg_stat_statements` уже «прогрет» |
| **B.** Полный рестарт сервиса | Сброс JVM | Чистый JIT, heap, метрики Micrometer; **необходим в любом случае** для смены `queue.executor.threadPoolSize` (читается на старте) | Требует прогрева перед прогоном |
| **C.** Прогрев перед прогоном | Sanity-warm-up на низкой нагрузке | Стабильные первые ступени | Удлиняет цикл; форма прогрева ещё не выбрана |
| **D.** Чистка WireMock state | Сброс `request journal` | Без ложных «совпадений» предыдущего прогона | Зависит от конфигурации стабов; может не понадобиться |
| **E.** Никакого tear-down | Прогоны идут подряд | Быстро | Эффект «прогретой БД» / накопления данных может отличать N=5 от N=10 не из-за воркеров |

**Решение принимается на встрече с командой.** В отчёте первой итерации фиксируется фактически использованный вариант — для воспроизводимости.

## 9. Формат отчёта первой итерации

Per-конфигурация (отдельно для N=5 и для N=10):

- **Предельный RPS = X** (последняя пройденная ступень).
- **Что произошло на следующей ступени** — рост backlog без стабилизации, появление ошибок какого типа, на каких метриках это видно.
- **График backlog** за весь прогон, с разметкой ступеней.
- **График Counter rate (поток успешных задач)** за весь прогон, с разметкой ступеней — для верификации факта нагрузки и сопоставления с backlog.
- **Графики двух error-метрик** за весь прогон (раздельно, см. §6).

В Claim Scope результата явно записано:

- что измеряли (нижняя часть системы);
- что **не** измеряли (`/cb`-цепочка, ТР ЕСИА, латентность задачи в очереди, burst);
- **идеализации стенда** (см. §3.1 — пять пунктов);
- **идеализации сценария A** (см. §3.2 — четыре пункта: один SNILS, один X-Bank-Id, один task_type, фиксированный набор `dataTypes`);
- **систематическое смещение стенд → прод** по polling-фактору (см. §3.1 п. 4 и §13.13);
- точность ответа = шаг ступени.

### 10.1 `queue.executor.threadPoolSize` — фактическое значение в master

`LOAD_TEST_PLAN.md` §2 указывает «`queue.executor.threadPoolSize=10`». Фактическое значение в `core/src/main/resources/application.yaml` master-ветки на момент составления этого плана — **`10`** (строка 51).

В исходной формулировке решений (M1.4) автор плана упоминал «текущее прод-значение, по словам автора, 5 (с возможной корректировкой)». Возможные расхождения:

- master vs прод-окружение могут отличаться;
- обсуждаемое значение «5» — возможно, целевая конфигурация, к которой команда планирует прийти, а не текущая прод-настройка.

**Открытый вопрос (см. §13.10):** какое значение `threadPoolSize` стоит в проде сейчас, и какая из двух конфигураций (N=5 / N=10) ближе к текущему прод-состоянию? Это нужно для интерпретации «что значит наш результат относительно прода» в финальном отчёте.

### 10.2 Реверс-СМЭВ как точка инжекции — пересмотр scope

В более ранних редакциях `LOAD_TEST_PLAN.md` «реверс-СМЭВ» исключался из scope. После уточнения терминологии в base plan §1 (реверс-СМЭВ = входящий HTTP-API «гейт→нас», не пуллер нотификаций) реверс-СМЭВ-API **в scope** общего плана и используется в сценариях B-HTTP и C. Эта итерация делает реверс-СМЭВ-API **точкой инжекции**.

**Причина первоначального исключения** реверс-СМЭВ из scope в более ранних редакциях не зафиксирована. **Открытый вопрос (см. §13.11):** автору base plan восстановить причину для архивной справки — была ли это терминологическая ошибка, или существовало содержательное возражение, которое мы упустили.

## 12. Алгоритм одного прогона (краткий рекап)

Не нормативный — конкретные команды и точная последовательность сборки стенда — в `LOAD_TEST_PLAN.md` §8.

1. На стенде установлено `queue.executor.threadPoolSize = N`. Сервис перезапущен.
2. Tear-down — по выбранному варианту (см. §8).
3. Открыт дашборд первой итерации (см. §7).
4. **Перед запуском прогона** — зафиксировать **базовое значение** Counter `dp_queue_tasks_processed_total` для каждого `result × taskType`, чтобы после прогона можно было посчитать дельту. Counter монотонный, без опорной точки дельта не считается.
5. Серия ступеней (см. §4): по очереди выставляем целевой RPS, держим 2 мин, **визуально** фиксируем вердикт по §5.
6. **Стоп-условия:**
   - Найдена непройденная ступень (первичный маркер).
   - Прошли все ступени без не-стационара → теоретический потолок занижен (см. §4.1) либо метрика «не докручена».
7. Завершение: вернуть RPS в 0, дать backlog'у рассосаться, снять финальные значения. Скриншоты Grafana — в раздел «Результаты» отчёта.

7. **HTTP-вход синхронно делает SOAP-вызов в адаптер** (§2.3, §4.1). На каждый POST `/smev/api/v1/PersonalData` сервис до возврата 200 OK выполняет `SmevService.sendAdapterRequest(...)` — это исходящий SOAP в адаптер (на стенде — WireMock ~150 мс). Один POST → два WireMock-вызова в разных местах жизненного цикла. Возможный эффект: HTTP-латентность POST'а на эндпоинт инжекции включает ≥ 150 мс WireMock-времени — это меняет интерпретацию вторичного маркера §6.1 и допущение «HTTP-вход — пренебрежимо малая работа», если такое допущение где-то использовано.
8. **Минимально-валидный JSON для `/PersonalData`** (§2.5). Из DTO `ReceivingPersonalDataDocWithScopeSmev3Request` нужно вытащить точный набор полей под Bean Validation — задача составителя Gatling-сценария, не часть этого плана.
9. **`threadPoolSize` в проде vs в master** (§10.1). master = 10, упомянутое автором прод-значение «5» нужно подтвердить.
10. **Endpoint реверс-СМЭВ-API** — `/PersonalData` или альтернативный `/CustomerPermissionList` (см. `PersonsSmevController.java:149-181`)? Оба создают задачи PERSON-типа, но разные DTO (`ReceivingPersonalDataDocWithScopeSmev3Request` vs `IssuedPersonPermissionsSmev3Request`) и разные `DataType` (`RECEIVING_PERSONAL_DATA_DOC_REQUEST` vs `ISSUED_PERSON_PERMISSIONS_REQUEST`). Решение — по обсуждению с командой; кандидат по умолчанию — `/PersonalData`.
11. **Реверс-СМЭВ — причина исключения в ранних редакциях base plan** (§10.2). Восстановить для архива.
12. **Версия СМЭВ на стенде** — 1.0.0/1.0.1 vs 1.0.2 (DO-11719). На 1.0.2 запрос ПДн идёт через промежуточную стадию запроса согласий (`PersonalDataSmevRequestHandler.supports()`), цепочка стадий длиннее, T_task другой. Чтобы числа N=5 и N=10 были сравнимы, обе конфигурации **должны идти на одной и той же версии**. Какую версию фиксируем для этой итерации — вопрос команды.

### Выявлены на M1.10 (сверка дизайна стабов с поведением прод-адаптера):

13. **Калибровочный коэффициент стенд → прод по polling-фактору** (§3.1 п. 4, §4.1). В проде один бизнес-запрос порождает N `GetResponseRequest`-обращений к адаптеру в стадии GetResponse (median зависит от реального времени готовности ответа в СМЭВ). На стенде N=1 (WireMock всегда `SUCCEEDED`). «Предельный RPS на стенде» — **верхняя граница** прод-предела по этой оси. Перенос требует измерения median N в прод-логах за репрезентативный период. Это **не задача этой итерации** — открытый вопрос для отчёта команде.
14. **Тестирование ветвей кода обработки ошибок адаптера** (§3.1 п. 2). Текущий стенд никогда не активирует код обработки 5xx/таймаутов/`PROCESSING`/`FAILED`/`NO_DATA` — эти ветки не покрываются нагрузочным тестом. Это **не цель** первой итерации (мы меряем стационарную пропускную способность счастливого пути). Но при пересмотре scope для следующих итераций — кандидат для отдельного теста на резильентность.
15. **WireMock-матчер по XML-содержимому, не по SOAP-структуре** (§3.1 п. 1). Зафиксировано как факт стенда, не открытый вопрос. Релевантно для интерпретации Claim Scope: изменения SOAP-обёртки в проде на стенде не отлавливаются. Если в команде есть ожидание, что нагрузочный тест поймает регрессию по SOAP-обёртке — это ожидание неверно, нужно зафиксировать в отчёте.

### Выявлены на M1.12 (реализация Counter `dp_queue_tasks_processed_total`):

16. **Регистрация Counter заранее для всех типов задач PERSON-стороны** (§6.2). В `QueueMetrics.@PostConstruct` зарегистрированы 6 строк (3 типа × 2 result: success/fail). При появлении ORG-задач или NONE-типа в трафике стенда — либо расширить регистрацию заранее (число строк по числу `TaskType`), либо явно фильтровать в `recordTaskProcessed`. Для первой итерации — не блокер (сценарий A работает только с PERSON), решение — при первом ORG-сценарии.
17. **Семантика β Counter — финальные исходы** (§6.2). Counter инкрементируется только на `COMPLETE` → `success` и `FAIL` → `fail`. Промежуточные статусы (`TRANSIENT_ERROR`, `NOT_READY`, `CHANGE_STATE`, `COMPLETE_AND_CREATE_NEXT`) не считаются. Это содержательное решение M1.12, **но** в команде должно быть явно зафиксировано — иначе «Counter показал N успехов» может быть неверно интерпретировано как «N бизнес-задач закрылось» (а если в трафике появляются `CHANGE_STATE` подзадачи — оба значения совпадают только частично).
18. **Метрика «временных ошибок при обработке»** (§6.2). Если возникнет потребность мерить «частоту ретраев» / «временных ошибок», это отдельный сигнал — другая метрика, или Counter с другой семантикой (учёт всех инкрементов состояния, не только финальных). Решение — следующая итерация.

### Выявлены на M1.14 (первый smoke-прогон + анализ Gatling-отчёта):

19. **Источник выброса латентности на ~4-й секунде smoke-прогона.** В smoke (1 RPS × 10 сек) один запрос из 10 выбился из основной массы (медиана 88 мс, max 274 мс). Кандидаты — JVM Young GC (5–200 мс), Hikari idle connection validation, ленивая инициализация singleton. На smoke не различимо. Для диагностики на следующих прогонах — добавить логи GC (`-Xlog:gc*`) и DEBUG-логи Hikari, либо использовать профайлер. Не блокер первой итерации, но материал для интерпретации tail-latency на ramp-up.
20. **Несимметрия грануляции Gauge vs Counter** (§5, §6.2). Gauge `dp_queue_tasks_backlog_size` зарегистрирован с тегом `taskType="person"` (агрегация по 3 PERSON-типам через фильтр в SQL). Counter `dp_queue_tasks_processed_total` использует разбивку по конкретному `taskType` (3 значения × 2 result). Это — содержательная асимметрия (Gauge про общий backlog «персоны», Counter про различение потоков по виду сведений). Но из Gauge нельзя сказать, какого именно типа задача находится в backlog. Если возникнет потребность видеть backlog по конкретному виду сведений — нужен либо отдельный Gauge на каждый тип, либо переход на per-type Gauge с тегом. Решение — при появлении смешанной нагрузки.
21. **Влияние состава `dataTypes` на размер обработки** (§3.2 п. 4). Тело POST первой итерации содержит фиксированный массив `dataTypes: ["inn", "RF_PASSPORT"]`. В проде состав варьируется, и это может влиять на размер обработки в воркере (например, разный объём данных для разных видов документов). Эффект на T_task — открытый вопрос; в первой итерации не моделируется.
22. **p99 на малых выборках вырождается до Max** (см. §7, §9). Алгоритм percentile: на N точках 95p и 99p в типичных реализациях совпадают с Max при `(100 − pct) × N / 100 ≤ 1`. Для p99 это значит — нужны минимум 100+ точек на ступени, чтобы p99 имел смысл отдельно от Max. На больших ступенях (5+ RPS × 2 мин = 600+ запросов) это уже выполнено. На warm-up и низких ступенях — p99 не интерпретируется отдельно от Max.

## Приложение B. Чего этот план НЕ говорит

- Не говорит о потолке **полного пути** (`/cb` → ТР ЕСИА → СМЭВ → задача → воркер).
- Не говорит о **латентности** задачи.
- Не говорит о **выборе финальной конфигурации**. Готовим **входные данные** для разговора, не вывод.
- Не говорит о **памяти / GC / БД-блокировках** как самостоятельных характеристиках. Они — за рамками первой итерации (см. §7.1, §13.4).
- Не говорит о **смешанной нагрузке** (одновременно несколько task_type / банков / форматов dataTypes). Это идеализации сценария §3.2.
- Не **закрывает** ни один из открытых вопросов §13.
- Не **калибрует** результат стенда на прод. Перенос «предельный RPS на стенде» → «предельный RPS в проде» требует измерения median N (polling-фактор) в прод-логах — это **не задача этой итерации** (§13.13).
