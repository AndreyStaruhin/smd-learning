# Stage 1 — Desired Understandings

## Essential question Модуля 1

**В чём разница между локальным нагрузочным тестом, который зелёный, и Enterprise-тестом, на который можно опираться при принятии решений о продакшне?**

Полная дисциплина активации, режим использования и falsifier ритуализации — в `project-systemprompt.md V7` раздел `# ESSENTIAL QUESTION МОДУЛЯ 1`. Этот вопрос — **опора возврата** для [Методолога] в моменте сдвига, не сценарий начала сессии.

## Enduring Understandings (центральные)

Шесть understandings, выявленных по эмпирике M1.1–M1.14 через ledger T-claims, T-кандидатов и зафиксированных сдвигов в reflection-log. Каждое — со ссылкой на эпизод проявления и текущим уровнем Evidence.

### EU1. Synthetic load is fiction (T закрыт M1.9 — claim M1-005)

Нагрузочный тест на стенде — симулякр реальной нагрузки, требующий явных идеализаций. Без идеализаций тест «зелёный по картинке», но не отвечает на инженерный вопрос. Идеализации — не дефект, а конструктивный элемент теста, который должен быть зафиксирован и проверен на cогласованность с инженерной целью.

**Эмпирика проявления:**
- M1.4: warm-up через предзагрузку BD как первая идеализация.
- M1.7: адаптер-заглушка как идеализация (тема 5 идеализаций §3.1 LOAD_TEST_ITERATION_1.md).
- M1.9: самостоятельное удержание позиции дважды в одной сессии — закрытие T.
- M1.10: декомпозиция через 5 идеализаций стенда (включая polling-разрыв главным риском).

**Уровень Evidence:** T закрыт M1.9. T → C — ждёт переноса на не-WireMock контекст.

### EU2. Decomposition «нагрузки» (T-кандидат M1-006)

«Нагрузка» — не одна метрика, а семейство метрик с разными моделями измерения, привязанными к разным точкам приложения (HTTP-вход / GET_RESPONSE / ACK_RESPONSE / BACKLOG / queue throughput). Вопрос «сколько RPS выдержит» некорректен без явной точки приложения.

**Эмпирика проявления:**
- M1.6: работа с точками приложения измерений (HTTP-вход / GET_RESPONSE / ACK_RESPONSE как разные стадии с разными моделями).
- M1.9: проявление T-кандидата при разборе сценариев A/B первой итерации.

**Уровень Evidence:** T-кандидат, ждёт независимого повторения для закрытия T.

### EU3. Онтологическая ось «продукт → адаптер → очередь адаптера → очередь СМЭВ → СМЭВ-3» (T-кандидат M1-007)

Видеть цепочку продукт ↔ внешний мир и где она режется в стенде первой итерации. Specialization EU1 (Synthetic load is fiction): идеализации — не абстрактные ограничения, а конкретные точки разреза цепочки.

**Эмпирика проявления:**
- M1.10: проявление T-кандидата через 5+ итераций упирания в [Критика] (учащийся 5+ раз неверно переворачивал направление цепочки).
- M1.13: применение в разборе границ сценария A.

**Уровень Evidence:** T-кандидат, использован в M1.13 — кандидат на закрытие T при следующем повторении в новом контексте.

### EU4. Запустить vs понять конфигурацию (T закрыт M1.12)

Конфигурация инструмента — не данность, а объект понимания. Что в classpath, какие методы видны при автокомплите (Java DSL vs Scala DSL в Gatling), как Counter инкрементируется, что делает inject profile, как `application.yml` Spring Boot складывается из distr-конфигурации и runtime-env.

**Эмпирика проявления:**
- M1.7: четыре сюрприза с расследованием (compose, Maven distr, Spring profiles).
- M1.10: предложение посмотреть журнал WireMock в момент проблематизации, принос кода `DelayPolicy` вместо ответа по памяти, гипотеза 4-го запроса с различением трафика.
- M1.12: закрытие T на Counter + Gatling в одной сессии.
- M1.13: третий контекст — DSL-конфигурация Gatling.
- M1.14: четвёртый контекст — рефакторинг baseUrl + сертификат.

**Уровень Evidence:** T закрыт M1.12. Кандидат на закрытие C в мета-сессии после первого релиза (4 контекста — достаточно для C при защите перед другим случаем).

### EU5. Природа Gauge как pull-метрика (T закрыт M1.14)

Метрика — не отчёт продукта, а объект с собственной природой (push vs pull, sampling, окно скрейпа Prometheus). Gauge даёт моментальные снимки и адекватную картину под нагрузкой; на одиночных запросах с долгим интервалом Gauge молчит.

**Эмпирика проявления:**
- M1.11: проявление T-кандидата при первой реализации Gauge `dp_queue_tasks_backlog_size`.
- M1.14: эпизод «один запрос на ~4-й секунде, Gauge молчит, увеличили поток до 5 RPS — Gauge поймал», самостоятельная формулировка учащимся «Gauge видит моментальные снимки, поэтому даёт адекватную картину только под нагрузкой» — закрытие T через far transfer (M1.11 → M1.14).

**Уровень Evidence:** T закрыт M1.14. Это первое явное far-transfer T-закрытие в курсе.

### EU6. Различение модели нагрузки и DSL (centerpiece, M1-001 in-progress)

Gatling — DSL для выражения модели нагрузки; модель нагрузки — отдельный объект, проектируемый **до** DSL. Inject profile (constantUsersPerSec / rampUsersPerSec / heavisideUsers) — это запись модели на DSL, не сама модель. Модель формулируется в терминах: точка приложения → распределение прибытия → профиль во времени → что считается «выдержать».

**Эмпирика проявления:**
- M1.2: первичное проявление в обсуждении вопроса «сколько RPS выдержит».
- M1.6: продвижение через работу с точками приложения измерений.
- M1.9: продвижение через эмпирические тайминги (113 мс — локальная обработка, не зависит от стаба).
- M1.13–M1.14: первая запись модели на Gatling DSL (constantUsersPerSec(5).during(10) для smoke).

**Уровень Evidence:** R закреплён, T в работе (in-progress). Закрытие T — на ramp-up прогоне 10→20→30→40→50→60 RPS как новом контексте применения модели.

## Что НЕ входит в Stage 1 (явно отрицаемое)

UbD требует явной фиксации того, что **не** претендует на enduring understanding. Это защита от coverage trap.

- **Performance tuning приложения.** Курс не учит делать продукт быстрее. Курс учит видеть, **где** он медленный.
- **SRE-практики и production observability.** Стенд первой итерации — не прод. Перенос — отдельная работа за рамками первого подхода.
- **Selenium / автоматизация callback ТР ЕСИА.** Реальный ТР ЕСИА — внешняя зависимость, ассигнована.
- **Альтернативные нагрузочные инструменты (k6, JMeter, Locust).** Out-of-scope по решению.
- **Архитектурное проектирование продукта.** Учащийся — разработчик продукта; в курсе он не как архитектор.
- **CI/CD-интеграция нагрузочных тестов.** M1.14 активный вопрос M1.13 — точка входа в Модуль 2, не Модуль 1.
- **Multi-instance configuration / soak tests / chaos engineering.** Out-of-scope.

## Что считать «не закрытым»

Рамка для проверки в конце первого подхода:
- Если критерии 1–4 закрыты, 5–8 в работе, 9 не начат → **Модуль 1 первым подходом не закрыт.** Откладывается на следующий подход. Это не провал; это пересмотр темпа MVP.
- Если критерии 1–9 закрыты → **Модуль 1 первым подходом закрыт.** Открывается Модуль 2, переход на CI-integration.
- Промежуточные конфигурации — обсуждаются на мета-сессии после первого релиза.

# Использование артефакта

## В каждой сессии

- Читается в Этапе 1 при сверке с состоянием курса (рядом с heat-map и evidence-ledger).
- В сессии **не редактируется**. Изменения вносятся только на ретроспективах.

## На ретроспективах

- **После M1.16 (короткая):** проверка операциональности B1/B2/B3 пилотов; правка Stage 2 (статусы критериев); правка Stage 3 (план M1.17+); правка Stage 1 — только если эмпирика M1.15–M1.16 проблематизировала какое-то EU.
- **После первого релиза (полная):** пересмотр MVP, темпа, всех Stage 1/2/3.
- **При смене подхода:** Stage 1 EU остаются; Stage 2 пересобирается полностью (новый MVP подхода 2); Stage 3 обнуляется.

## Falsifier ритуализации артефакта

См. `project-systemprompt.md V7` раздел `# МОДУЛЬНЫЙ BACKWARD DESIGN (РЕТРОСПЕКТИВНЫЙ)`. Признаки отзыва пилота:
- Stage 1/2/3 ритуализуются (формальная сверка без операционального следствия).
- Stage 1 становится прокрустовым ложем для эмпирики, не входящей в EU1–EU6.
- Сложность поддержки артефакта превышает выгоду — обновление становится бременем.

При срабатывании 2+ сигнала за 4+ сессии — отзыв B3, артефакт переводится в архивное состояние с пометкой эмпирики, опровергающей пилот.
